# Fastify и Express для GraphQL

Статус на 2026-11-07: HTTP-платформа визитки — штатный адаптер Express, GraphQL-движок — Apollo, страница проверяющего — Apollo Sandbox на маршруте `/graphql`. Краткое решение и цена — [decisions.md](decisions.md), блок 1. `src/main.ts` делает `NestFactory.create` без смены адаптера, включает shutdown hooks и слушает порт. Маршрут `/graphql`, схема code-first и Sandbox собраны в `src/app.module.ts`. Путь одного запроса от страницы до резолвера — в [bridge.md](bridge.md).

Заметка собрана из одного разговора: что такое Sandbox, чем GraphQL является как API, почему маршрут один, кто такой Apollo, зачем под ним Express, есть ли у Nest отдельный сервер под GraphQL, чем Fastify отличается по устройству и сложности и как оба HTTP-сервера садятся на GraphQL.

## Ключевые выводы

1. GraphQL — язык запроса и правила контракта. API визитки — один HTTP-маршрут `/graphql`. Сервером GraphQL сам по себе не является.
2. В REST ресурс выбирает путь (`/api/profile`, `/api/skills`). Здесь путь всегда один. Что прочитать, написано в теле POST: корневое поле `profile` и вложенные поля. GET `/graphql` открывает страницу Sandbox, POST на тот же адрес исполняет запрос. Контроллера `@Get('profile')` на этом пути нет.
3. Apollo исполняет GraphQL: сверяет текст со схемой, вызывает резолвер, собирает JSON из выбранных полей и отдаёт landing page. Express принимает соединение, разбирает тело и слушает порт. GraphQL Express не подменяет.
4. Отдельного «Express для GraphQL» в Nest нет. Другой HTTP-адаптер — Fastify. Другой GraphQL-движок, и только вместе с Fastify, — Mercurius. Apollo на Fastify по-прежнему умеет открыть Sandbox. Mercurius открывает GraphiQL и пункт ТЗ про Apollo Sandbox сам не закрывает.
5. Для визитки оставлены Express и Apollo. ТЗ требует Sandbox. Сценарий — одно чтение профиля. Выигрыш Fastify на таком запросе почти не виден: форму JSON выбирает текст запроса, и ответ собирает Apollo. Сложность Fastify — второй набор понятий (хуки, JSON Schema маршрута, плагины, `request`/`reply`) на живой правке, где смотрят резолвер и Prisma.
6. Цена выбора — высокопроизводительный режим Nest в этой визитке не исследуется. Для тестового и для правки на собеседовании это приемлемо.

## Apollo Sandbox

Строка ТЗ: приложение должно предоставлять Apollo Sandbox, через которое можно получить профиль, опыт, навыки и проекты.

Apollo Sandbox — встроенная страница Apollo Server в браузере. С неё пишут GraphQL-запрос и сразу видят ответ. По роли она близка к Swagger UI: схема и пробный запрос живут на том же сервере. Отдельный сервис поднимать не нужно.

Проверяющий открывает `/graphql`. Sandbox читает схему интроспекцией: сервер отдаёт перечень своих типов и полей. На странице оказывается ровно тот контракт, который Nest собрал из классов с `@ObjectType` и `@Field`. Дальше в редакторе набирают запрос из ТЗ и получают JSON.

Это штатная landing page текущего Apollo Server. Старый GraphQL Playground у этого сервера больше не является такой страницей. Включение Sandbox — `ApolloServerPluginLandingPageLocalDefault` в `GraphQLModule.forRootAsync` (`src/app.module.ts`). Рядом стоят `graphiql: false` и `playground: false`: при выключенном `graphiql` драйвер Nest глушит неявную landing page, поэтому Sandbox включён явным плагином. `introspection: true` нужно странице, чтобы прочитать схему. `autoSchemaFile: true` держит эту схему в памяти.

## GraphQL как API

GraphQL — язык запросов и правила контракта API. Слово само по себе не обозначает процесс, который слушает порт.

API — то, что приложение отдаёт наружу. В визитке это HTTP-маршрут `/graphql`. Контракт маршрута описан схемой: типы и поля `profile`, `skills`, `experience`, `projects`. Клиент присылает текст запроса, сервер сверяет его со схемой и возвращает JSON только с выбранными полями.

Та же роль у REST: контракт плюс HTTP. У визитки контракт — схема GraphQL, транспорт — HTTP POST на `/graphql`.

## Один маршрут вместо набора `/api/...`

Весь контракт визитки живёт на `/graphql`, строчными. Путей `/api/profile` и `/api/skills` нет.

В REST ресурс выбирает путь: `GET /api/profile`, `GET /api/skills`. Здесь «что прочитать» лежит в теле. POST на `/graphql` несёт JSON с текстом:

```graphql
query {
  profile {
    name
    skills { name }
  }
}
```

Корневое поле `profile` — вход сценария. Вложенные `skills`, `experience`, `projects` — выбор полей внутри того же запроса. Это другие поля схемы, а не другие URL.

Тот же адрес открывается в браузере. GET `/graphql` отдаёт HTML страницы Apollo Sandbox. Запросы из неё уходят POST-ом на этот же маршрут. Express принимает соединение и отдаёт его Apollo.

Имя маршрута фиксировано: `/graphql`. Вариант `/graphQL` в решение не входит.

## Кто такой Apollo и зачем под ним Express

Apollo в этой визитке — библиотека, которая исполняет GraphQL. Nest подключает её через `@nestjs/graphql`. Она сверяет текст запроса со схемой, вызывает резолвер профиля и собирает JSON только из выбранных полей. Страница Apollo Sandbox — её же landing page: схема приходит интроспекцией, запрос уходит обратно на тот же маршрут.

Express — HTTP-сервер под Nest, штатный адаптер. Он слушает порт, принимает соединение и разбирает тело запроса. Маршрут `/graphql` стоит на этом Express-приложении.

На одном запросе цепочка такая. Браузер делает POST `/graphql`. Express принимает HTTP. Apollo исполняет текст. `ProfileResolver` вызывает сервис и репозиторий. Loader-ы этого запроса создаёт context-функция в `src/app.module.ts`. `listen` и shutdown hooks по-прежнему в `src/main.ts`.

Nest по-прежнему поднимает один процесс Node. Знакомое из Express остаётся под GraphQL: входящий HTTP, разбор тела, ответ JSON, `listen`. Знакомое из Nest REST тоже остаётся: модуль, сервис, внедрение в конструктор, чтение окружения при старте. Пайпы и `ValidationPipe` на чтении визитки не нужны: у поля `profile` нет аргументов и нет тела с полями пользователя.

## Есть ли в Nest отдельный сервер под GraphQL

Отдельного HTTP-сервера «для GraphQL» Nest не даёт. Express остаётся сервером соединения и тогда, когда API описан схемой GraphQL. Понимает текст запроса Apollo. Nest сажает его на `/graphql` через `@nestjs/graphql`.

Другой HTTP-адаптер Nest — Fastify. Это замена на уровне соединения, порта и тела запроса. К языку GraphQL она не привязана. В визитке оставлен Express: отладка соединения остаётся в привычной модели, а выигрыш Fastify этому приложению не нужен.

## Чем Fastify отличается и где сложность

Оба закрывают одну задачу в Nest: принять HTTP, разобрать тело и отдать ответ. Код резолвера, сервиса и Prisma от выбора адаптера не меняется. Меняется обвязка соединения.

Express — минимальный сервер на цепочке middleware. Запрос идёт через функции `(req, res, next)`, ответ пишет обработчик. Схемы тела у фреймворка нет: разбор JSON и проверки добавляются отдельно. В Nest это штатный адаптер, и он совпадает с маршрутами, которые уже писались на Express и в Nest REST.

Fastify — сервер с плагинами, хуками и JSON Schema. Схему маршрута он использует и для проверки входа, и для сборки JSON-ответа. Пропускная способность выше, накладные расходы на соединение ниже. API другое: `request` / `reply` и хуки, а не `req` / `res` / `next`. Плагины изолированы по области видимости. Middleware Express подключается через слой совместимости, работает не весь, и часть выигрыша по скорости при этом теряется.

Сложность для визитки маленькая в обе стороны, потому что почти весь трафик — один маршрут `/graphql`, который забирает Apollo. Разница всплывает там, где трогают сырой HTTP: порт, тело, куки, свои middleware, типы запроса. На Fastify это другой адаптер и другая отладка соединения. Выигрыш в скорости на одном читающем профиле не виден.

Поэтому в блоке 1 [decisions.md](decisions.md) оставлен Express. Платим тем, что высокопроизводительный режим Nest не исследуем.

## Как каждый садится на GraphQL

Оба применимы к GraphQL на одну и ту же глубину: они доставляют HTTP. Разбор текста, сверка со схемой и вызов резолвера делает GraphQL-движок на маршруте `/graphql`.

Express и Apollo — штатная пара Nest. Express принимает POST и GET `/graphql`. Apollo исполняет запрос и отдаёт Apollo Sandbox. Резолвер, loader и Prisma адаптер не видят. Sandbox прямо требуется ТЗ, поэтому пара закрывает и транспорт, и страницу проверяющего.

Fastify несёт тот же протокол: POST с текстом запроса, ответ JSON. В экосистеме Nest его сажают двумя способами.

- Тот же Apollo на адаптере Fastify. Sandbox остаётся, потому что страницу рисует Apollo. Меняется приём соединения: хуки и `request`/`reply`. Для визитки это тот же контракт и другая обвязка в `main.ts`.
- Mercurius — GraphQL-движок под хуки Fastify. Он умеет кешировать уже разобранный запрос и теснее связан с жизненным циклом Fastify. Страница по умолчанию у него GraphiQL. Apollo Sandbox он не открывает. Пункт ТЗ про Sandbox таким выбором сам не закрывается.

После входа в Apollo разницы между адаптерами почти нет. Схема, поле `profile`, field resolver-ы и чтение Prisma идут одним путём. Адаптер заметен в регистрации маршрута, разборе тела и в том, какой объект запроса попадёт в context-фабрику loader-а.

## Как устроен Fastify

Fastify занимает то же место, что Express: порт, соединение, тело, ответ. В Nest он подключается своим адаптером платформы. Резолвер, сервис и Prisma при этой замене не переписываются.

Запрос у Express проходит цепочку middleware. Каждая функция получает `req`, `res` и `next` и сама решает, писать ли ответ. У Fastify набор хуков с фиксированным порядком: запрос пришёл, тело разобрано, вход проверен, обработчик вызван, ответ собран, ответ ушёл. Обработчик получает `request` и `reply` и заканчивает ответ через `reply.send()`.

Проверка входа и форма ответа описываются JSON Schema рядом с маршрутом. Схему Fastify компилирует один раз при старте. Вход проверяется по ней. Ответ, если схема задана, собирает сериализатор, подготовленный по этой схеме. Логер — Pino, он входит в процесс.

Скорость складывается из быстрого поиска маршрута, дешёвых объектов запроса и сериализации по заранее собранной схеме. На REST-маршруте с фиксированным JSON это заметно. На GraphQL слабее. Форму ответа выбирает текст запроса, одну схему ответа заранее не описывают, JSON собирает Apollo. От Fastify на таком маршруте остаётся более лёгкий приём соединения. Время запроса почти целиком уходит на разбор GraphQL, резолверы и базу.

Код подключают плагинами. У плагина свой контекст: декораторы и хуки внутри снаружи не видны, пока плагин явно не откроют. Так части приложения изолированы. Куки, сессии и загрузка файлов — отдельные пакеты Fastify, со своими типами, а не пакеты под `req` и `res`.

В Nest контроллеры и провайдеры выглядят так же. Другим становится сырой HTTP: тип объекта запроса, свои middleware, разбор тела, логи. Для визитки это понятия, которые проверяющий на сценарии «прочитать профиль» не требует. Смотреть он будет резолвер, слои и Prisma. Второй HTTP-стек на живой правке добавляет поверхность, которой нет в ТЗ.

## Почему в визитке Express

Пять вопросов, как у остальных заметок конспекта.

1. Выбрано: штатный HTTP-адаптер Express и Apollo как движок GraphQL со страницей Sandbox.
2. Продолжение практики: тот же `listen`, тот же приём соединения и разбор тела, что в Express и в Nest REST. Раньше путь выбирал ресурс. Теперь путь один, ресурс выбирает текст запроса, а исполняет его Apollo.
3. Отличие от Fastify: другие объекты запроса, хуки и схема маршрута, другой способ сериализовать фиксированный JSON, другой GraphQL-движок Mercurius, если уходить с Apollo. На запрос визитки после входа в Apollo путь данных тот же.
4. Почему так: ТЗ требует Apollo Sandbox. Один читающий профиль не показывает выигрыш Fastify. Отладка порта и тела остаётся в модели, которая уже знакома. Правка на собеседовании попадает в модуль профиля, а не в замену адаптера.
5. Чем платим: высокопроизводительный режим Nest не исследуется. Выбор адаптера лежит в `src/main.ts` (`NestFactory.create` без замены). Регистрация `/graphql` и Sandbox — `src/app.module.ts`. Сравнение, почему адаптер не меняли, — этот файл. Короткое решение — блок 1 в [decisions.md](decisions.md).
