# Решения

Статус на 2026-11-07: чтение визитки собрано в коде. Ниже то, что делают текущие файлы `it_smi-server`. Шаблон блока прежний: выбор, продолжение практики Express или Nest REST, отличие, почему так в визитке, чем платим и в каком файле это лежит.

## 1. HTTP-платформа — Express, порт и остановка

Выбрано: штатный адаптер Express. `NestFactory.create(AppModule)` не получает адаптер Fastify. В зависимостях стоит `@nestjs/platform-express`. Слушает процесс порт из проверенного env и перед этим включает хуки остановки Nest.

В Express ты сам вызывал `app.listen` и сам закрывал сервер на сигнал. В Nest REST то же заканчивается `app.listen`, только модули собирает фабрика. Здесь вызов тот же. GraphQL занимает маршрут этого процесса, отдельного HTTP-сервера у него нет.

Отличие от Fastify то же, что было в решении: другой адаптер и другая обвязка соединения ради скорости, которую одно чтение профиля не показывает. Разбор, почему адаптер не меняли, лежит в [Fastify_vs_Express_for_GraphQL.md](Fastify_vs_Express_for_GraphQL.md).

`enableShutdownHooks()` нужен, потому что соединение с Postgres держит `PrismaService`. Хук модуля вызывает `$disconnect` на остановке. Без хуков процесс мог бы выйти и оставить клиент висеть. Сигнал доходит до Node, потому что entrypoint контейнера подменяет shell на `node` через `exec`. Это уже холодный старт, блок 10.

Платим тем, что высокопроизводительный режим Nest не исследуется. Для тестового и для живой правки это приемлемо.

Место: `src/main.ts`. Сборка и запуск — `nest build`, `nest start`, для разработки `nest start --watch` (`npm run start:dev`). Готовый процесс — `node dist/main` (`npm run start:prod`). TypeScript 6.0.3. Node в `engines` — 26, базовый образ — `node:26-bookworm-slim`.

Проверка окружения включается в том же старте модуля. `ConfigModule.forRoot({ isGlobal: true, validate: validateEnv })` в `src/app.module.ts` вызывает `src/config/env.ts` до приёма трафика.

Выбрана явная функция, а не чтение `process.env` по месту. В Nest REST ты уже ловил кривой env на старте, чтобы не узнать о пустой строке из середины запроса. Здесь тот же момент: процесс либо поднимается с `AppEnv`, либо падает на `validate`.

Отличие от «просто прочитать переменную»: `PORT` можно не задавать, тогда порт 3000; заданный порт — целое от 1 до 65535. `DATABASE_URL` обязателен, строка должна разбираться как URL, схема только `postgresql:` или `postgres:`. `ConfigService<AppEnv, true>` в `main.ts` и в `PrismaService` берёт уже проверенные `port` и `databaseUrl`.

Почему так: визитка без базы не имеет смысла, а Sandbox на случайном порту ломает сценарий «открыл compose и смотришь `/graphql`». Платим отказом старта на опечатке в URL. Seed эту функцию не вызывает: у него свой процесс и своя, более узкая проверка непустой строки. Два читателя одной переменной — плата за то, что seed не импортирует Nest.

## 2. Один агрегат, один модуль

Вся визитка — один агрегат. Навыки, опыт, достижения, проекты и ссылки существуют как связи профиля. Код сценария лежит в `src/profile/`. Рядом отдельный `src/prisma/`: он даёт клиент базы всему процессу, это не второй сценарий.

В Express это был бы один роутер. В Nest REST — один модуль с контроллером. Отдельный модуль на каждую таблицу размазал бы «прочитать визитку» по папкам, которые друг без друга не работают.

`ProfileModule` импортирует `PrismaModule` и регистрирует репозиторий, сервис, фабрику loader и два резолвера: `ProfileResolver` и `ExperienceResolver`. Наружу модуль отдаёт только `ProfileLoaderFactory`: она нужна фабрике GraphQL в `AppModule`.

Платим плотностью одной папки. Граница, которая её удерживает, — слои внутри, а не новые модули. Второй модуль появится вместе со вторым сценарием. У текущего чтения визитки такой причины нет.

## 3. Три слоя и три контракта

| Слой | Файл | Делает |
| --- | --- | --- |
| GraphQL | `profile.resolver.ts`, типы в `profile.objects.ts` | форма API; сервис корня и loader текущего запроса |
| Сценарий | `profile.service.ts` | «прочитать визитку владельца»: скаляры или `null` |
| Данные | `profile.repository.ts` | чтение Prisma и перевод строки в доменный тип |

Перевод строки собран в `profile.mapping.ts`. Это шов репозитория, не четвёртый сценарий и не схема GraphQL.

В Express обработчик маршрута часто сам ходит в базу и пишет `res.json`. В Nest REST ты уже отделял контроллер от сервиса. Здесь третье звено жёсткое. Резолвер не вызывает Prisma. Сервис не носит `@Query` и `@ResolveField` и не пишет условия запросов. Репозиторий не собирает ответ GraphQL и на пути запроса только читает.

Сервис тонкий нарочно. Весь его сценарий: взять стабильный ключ `PROFILE_OWNER_KEY` (`'owner'` в `profile.owner-key.ts`) и вернуть то, что нашёл репозиторий, включая отсутствие строки. Правила календаря и порядка списков живут в маппинге и в `orderBy` репозитория.

Три контракта не смешиваются:

- домен сервиса — интерфейсы `profile.types.ts`;
- схема GraphQL — классы `@ObjectType` в `profile.objects.ts`;
- модели Prisma остаются у `PrismaService`, у методов репозитория и у `prisma/seed.ts`.

`id` есть у доменных `ProfileCard` и `Experience`, потому что loader-у нужен родитель. На классах GraphQL поля `id` нет, `ownerKey` нет, `sortOrder` нет. Клиент их не спрашивает. `@Parent()` получает доменный объект целиком, а в JSON уходят только свойства, для которых есть `@Field` или `@ResolveField`.

```typescript
export interface ProfileCard {
  readonly id: string;
  readonly name: string;
  readonly description: string;
}
```

```typescript
@ObjectType('Profile')
export class ProfileType {
  @Field(() => String)
  name: string;

  @Field(() => String)
  description: string;
}
```

Резолвер возвращает `ProfileCard`, не экземпляр `ProfileType`. Имена общих полей обязаны совпадать: GraphQL снимает `name` и `description` с доменного объекта.

Так сделано, потому что новое поле API не должно переписывать SQL, а смена чтения не должна переписывать схему. Платим явным перекладыванием там, где в небольшом REST-сервисе хватило бы одного DTO. На визитке полей мало, маппинг короткий. Сырой результат Prisma в `@Parent()` не передаётся: репозиторий сразу вызывает `mapProfile`, `mapSkill` и соседние функции. Форма `select` проверяется типами строк в `profile.mapping.ts` (`ProfileScalarRow` и остальные), это не тип модели Prisma и не класс `@ObjectType`.

## 4. Схема из TypeScript, страница — Apollo Sandbox

Схему описывают классы и резолверы (code-first). Отдельного файла `.graphql` в приложении нет: `autoSchemaFile: true` держит схему в памяти.

Это прямое продолжение DTO в Nest REST: класс, декоратор, по декораторам фреймворк собирает контракт. `@ObjectType` и `@Field` описывают скаляры ответа. Вложенные коллекции в классы не вписаны: их добавляют методы `@ResolveField`. `@Query` для входа `profile` играет роль `@Get`.

Schema-first дал бы второй источник правды рядом с TypeScript. Его берут, когда схему пишут раньше кода или ею владеет другая команда. Здесь владелец один, язык проекта — TypeScript.

Имена полей совпадают с примером задания: корень `profile`, у навыка `name`, у опыта `company` и `position`, у проекта `name`. Рядом в тех же типах лежат остальные поля чтения: `description`, ссылки `label` и `url`, период `period { kind on }`, `achievements { text }`, у проекта ещё `url`.

Страница проверяющего — Apollo Sandbox, landing page текущего Apollo Server (`@apollo/server` 5.5.1, драйвер `@nestjs/apollo`). Старый Playground этой страницей не является. Sandbox читает схему интроспекцией и показывает ровно тот контракт, который собрали декораторы.

Включение сидит в `GraphQLModule.forRootAsync` в `src/app.module.ts`, не в `main.ts`:

```typescript
path: '/graphql',
autoSchemaFile: true,
graphiql: false,
playground: false,
introspection: true,
plugins: [ApolloServerPluginLandingPageLocalDefault()],
```

`graphiql: false` и `playground: false` стоят сознательно. При выключенном `graphiql` драйвер Nest добавляет плагин, который глушит неявную landing page Apollo. Sandbox поэтому включён отдельным `ApolloServerPluginLandingPageLocalDefault`. GET `/graphql` открывает эту страницу, POST на тот же путь исполняет запрос.

Платим привязкой к code-first и публичной интроспекцией на этом порту: Sandbox без неё схему не покажет. Смешивать ручной `.graphql` с декораторами в этом приложении нечем: схема живёт в классах и резолверах. Отдельного файла схемы в git нет, смотреть контракт нужно по `profile.objects.ts` и `profile.resolver.ts`.

## 5. Корень, вложенные поля и чтение только выбранных связей

Корневое поле одно, без аргумента `id`.

```typescript
@Query(() => ProfileType, { nullable: true })
profile(): Promise<ProfileCard | null> {
  return this.profileService.readOwner();
}
```

`nullable: true` — часть контракта. Нет строки владельца — ответ `profile: null`, не HTTP 404. В Nest REST отсутствующую сущность ты часто превращал в `NotFoundException`. Здесь клиент Sandbox видит пустое поле и сразу понимает, что seed не записан. Платим тем, что запрос обязан выдержать `null`. Field resolver-ы при `null` не вызываются: родителя нет.

Корень читает скаляры строки профиля. `findByOwnerKey` делает `findUnique` по `ownerKey` и выбирает `id`, `name`, `description`. Ключа `include` у этого вызова нет. `id` нужен детям и в JSON не входит; колонки связей этот запрос не открывает. Набор колонок фиксированный: запрос одного `name` всё равно читает `id` и `description` той же строки, потому что они лежат в ней. Таблицы навыков, опыта и проектов при этом не читаются.

Коллекции отдают `@ResolveField`. `links`, `skills`, `experience` и `projects` висят на `ProfileResolver` и грузят связь по `profile.id`. `period` и `achievements` висят на `ExperienceResolver` и грузят связь по `experience.id`. Опыт сам их не подмешивает: `findExperienceByProfileIds` в `select` берёт только компанию и должность. Пока клиент не написал `period` или `achievements`, соответствующий loader не вызывается. Запрос из задания как раз такой: `experience { company position }` опыт читает, период и достижения нет.

Пустой список id репозиторий в базу не отправляет. Порядок элементов задаёт `orderBy` по родителю и `sortOrder`, не резолвер.

Почему корень не делает `include` всего дерева. Для одного профиля так было бы короче. Тогда `profile { name }` всё равно притащил бы опыт и проекты, а field resolver только притворялся бы решением о загрузке. Платим отдельным чтением на каждую выбранную связь даже у одного владельца. Запрос платит только за написанные поля.

Это поведение корня закреплено тестом `src/profile/profile.repository.spec.ts`: в аргументах `findUnique` есть `select` трёх скаляров и нет `include`. Живой лог SQL с поднятого сервера в конспект не снимался.

## 6. Контекст запроса и свой batch loader

Пакет библиотеки DataLoader в проект не входит. Сбор одинаковых чтений делает `createBatchLoader` в `src/profile/profile.batch-loader.ts`. Идея та же, что у DataLoader в рассказе про GraphQL: за один заход к базе забрать связь для набора родителей и не устроить N+1. Продолжение для тебя — не middleware Express и не интерцептор Nest, а группировка, которую в REST ты делал бы сам, если бы один endpoint принимал список id.

Отличие от готового DataLoader: ответ репозитория — `Map` по id родителя, а не массив, выровненный по позиции входного списка. Каждый ожидающий `load` получает `grouped.get(key)` или пустой замороженный список. Ключ, которого в карте нет, даёт `[]`, поэтому список в GraphQL остаётся списком. Коллекции объявлены методами `@ResolveField(() => [SkillType])` и аналогичными, без `nullable: true`. Пустая связь приходит пустым массивом, который собрал loader.

Фабрика Nest одна на процесс. Экземпляры loader — нет. `GraphQLModule` на каждый запрос вызывает context-функцию, а она вызывает `ProfileLoaderFactory.create()`:

```typescript
context: () => ({
  loaders: loaderFactory.create(),
}),
```

`create()` собирает шесть loader-ов. Четыре зовут методы `find…ByProfileIds`. `findAchievementsByExperienceIds` и `findPointsByExperienceIds` зовутся по id опыта. Репозиторий при этом singleton и кэш запроса не хранит. Кэш — карта обещаний внутри замыкания `createBatchLoader`. Новый `create()` прежних ключей не видит. Если бы кэшем был сам провайдер Nest, ключи жили бы между запросами.

Внутри одного экземпляра `load` копится до конца синхронного куска и уходит одним `queueMicrotask`. Повтор того же ключа в этом микротакте дедуплицируется. Следующий `load` уже известного ключа возвращает прежнее обещание и базу второй раз не зовёт. Ошибка выборки тоже запоминается на время экземпляра: повтор в том же запросе не долбит базу.

Field resolver базу не открывает. Он просит loader контекста:

```typescript
@ResolveField(() => [SkillType])
skills(
  @Parent() profile: ProfileCard,
  @Context() context: ProfileGraphqlContext,
): Promise<readonly Skill[]> {
  return context.loaders.skills.load(profile.id);
}
```

Почему свой код, а не пакет. Визитке нужна одна операция: по списку id родителя вернуть списки детей. Позиционный контракт DataLoader здесь легко объяснить неверно, карта родителя читается прямо. Платим поддержкой очереди, дедупликации и кэша ошибки. Поведение зафиксировано в `src/profile/profile.batch-loader.spec.ts`.

Один профиль делает лишний запрос на связь почти незаметным. Приём всё равно сразу такой: несколько `load` одного родителя остаются одним чтением. На собеседовании список профилей не превращает это в N+1.

## 7. Prisma, адаптер `pg` и PostgreSQL

База — PostgreSQL. В compose это сервис `postgres:17-alpine`, приложение ждёт его healthcheck `pg_isready`. Схема таблиц — `prisma/schema.prisma`, каталог миграций указан в `prisma.config.ts` как `prisma/migrations`. Клиент Prisma 7.10.1 генерируется в `src/generated/prisma`. Строка соединения в рантайме приложения в схему не зашита: её получает драйвер.

`PrismaService` — один клиент процесса Nest. Он наследует сгенерированный `PrismaClient` и живёт в `PrismaModule`, который его экспортирует.

```typescript
const adapter = new PrismaPg({
  connectionString: config.get('databaseUrl', { infer: true }),
});
super({ adapter });
```

Prisma 7 ходит в Postgres через адаптер. Здесь это `@prisma/adapter-pg` и пакет `pg`. В Express ты открывал `pg.Pool` сам. В Nest REST с TypeORM таблица часто была декораторами на том же классе, что и DTO. Здесь таблица описана в `schema.prisma`, а класс GraphQL таблицей не является.

Жизненный цикл — хуки модуля, те же `OnModuleInit` / `OnModuleDestroy`, что ты уже вешал на клиент в Nest REST:

```typescript
async onModuleInit(): Promise<void> {
  await this.$connect();
}

async onModuleDestroy(): Promise<void> {
  await this.$disconnect();
}
```

`$connect` проходит при старте модуля, `$disconnect` — когда срабатывают shutdown hooks из блока 1. Seed этот сервис не использует: у него свой `PrismaClient` и свой `PrismaPg` в отдельном процессе.

PostgreSQL выбран потому, что он в стеке вакансии и является штатной реляционной целью Prisma. Поднимать визитку на другом движке значило бы репетировать не ту базу.

Репозиторий читает модели `profile`, `profileLink`, `skill`, `experience`, `experiencePoint`, `achievement`, `project`. Связи он фильтрует по `profileId` или `experienceId`. Комментарий seed дополнительно опирается на `onDelete: Cascade` у точки периода и достижения при удалении опыта. Текст `schema.prisma` и файлы миграций в этой сверке конспекта не открывались: имена колонок ниже взяты из `select` репозитория и из записи seed.

Платим ручным отображением и отдельным адаптером там, где старый Prisma принимал URL прямо в схеме. S3 нет: у визитки нет файлов, хранилище подключать не к чему.

## 8. Пишет только seed

Публичный контракт — чтение `profile`. Мутаций в резолвере нет. Единственный писатель данных — `prisma/seed.ts`. Команда Prisma задана в `prisma.config.ts`: `node --import tsx prisma/seed.ts` (`npm run seed` → `prisma db seed`). Файл не импортирует резолверы и сервисы Nest. Ключ владельца продублирован локальным литералом `'owner'`, тем же, что `PROFILE_OWNER_KEY`. Импорт профильного модуля из seed разорвал бы эту границу. Плата — два литерала, которые должны остаться равными; оба файла это прямо комментируют.

Повторный запуск не копирует визитку. Одна транзакция делает `upsert` профиля по `ownerKey` и затем заменяет его детей:

- удаляет точки периода и достижения этого профиля, затем опыт, ссылки, навыки и проекты;
- заново пишет набор из seed;
- точки периода и достижения создаёт вложенной записью при создании опыта.

Удаление детей идёт и без каскада: сначала точки периода и достижения, потом опыт. Откат транзакции снимает и upsert, если замена детей упала. Идемпотентность здесь — «снова тот же набор», не «upsert каждой дочерней строки». Идентификатор профиля сохраняется. Идентификаторы детей после каждого seed новые, потому что строки удалены и созданы заново. Loader на старые id между запусками не опирается.

Seed пишет одного владельца фактами резюме. Шесть мест идут от позднего к раннему, индекс в массиве становится `sortOrder`. Текущая проектная работа открыта: записи `END` нет. Окна без записи есть после августа 2015 до ноября 2015 и после декабря 2025 до апреля 2026. Смежные роли стыкуются в одном месяце резюме. У проектов без публичного адреса `url` пустой: адрес в seed не выдумывается.

Даты в seed собираются как полночь UTC из частей `YYYY-MM-DD`, без локального конструктора `Date`. Иначе западная зона сдвигает календарный день ещё до записи.

Seed проверяет только то, что `DATABASE_URL` — непустая строка. Протокол URL проверяет `validateEnv` при старте Nest, не seed. Ошибку seed печатает после вырезания строки соединения из текста. В `finally` клиент seed вызывает `$disconnect`, отдельно от `PrismaService`. Прямой запуск файла определяется по пути входа: импорт модуля сам запись не начинает.

Платим тем, что биографию меняют seed-ом и перезапуском, а не мутацией из Sandbox. Это совпадает с поставкой данных при старте.

## 9. Форма данных и день `YYYY-MM-DD`

Связи, которые клиент выбирает по отдельности, лежат строками родителя и читаются loader-ом из блока 6.

- Ссылки — записи «метка + url». Новая ссылка не добавляет колонку профиля.
- Период места работы — записи `ExperiencePoint`. Поле `kind` делает запись начальной (`START`) или завершающей (`END`). День — `on`, в GraphQL обязательный `String`. Записи `END` может не быть. Свой loader, родитель — опыт.
- Достижения — отдельные записи с текстом и `sortOrder`, не массив текста на строке опыта. Свой loader, родитель — опыт.
- Проект — название и url.
- Пустая связь в ответе — пустой список.

В PostgreSQL день приходит как `Date`. Комментарий маппинга фиксирует путь: adapter-pg отдаёт календарную строку, а клиент дополняет её до полуночи UTC. В домен и в GraphQL уходит уже строка `YYYY-MM-DD`. Отдельный скаляр GraphQL для даты не вводился: у визитки один формат дня, новая зависимость для него не нужна.

```typescript
const year = value.getUTCFullYear();
const month = value.getUTCMonth() + 1;
const day = value.getUTCDate();
```

День собирается из UTC-частей. Локальные `getFullYear` / `getDate` в зоне с отрицательным смещением сдвинули бы полночь UTC на предыдущие сутки. `formatCalendarDate` ещё отбрасывает недату. `mapExperiencePoint` форматирует `on`. `mapExperience` дату не несёт: период читается отдельно. Seed пишет тот же UTC-день, чтение его же и показывает. `mapExperiencePointKind` отбрасывает значение кроме `START` и `END`.

`String` сам формат не проверяет. Платим проверкой на границе seed и репозитория. Тест `src/profile/profile.mapping.spec.ts` держит UTC-полночь, високосный день и отказ на недате.

Платим и лишними таблицами там, где хватило бы пары колонок и массива текста. Взамен коллекции в резолвере устроены одинаково: родитель, loader, одна выборка по id. Ключ владельца один, аргумента `id` у поля `profile` нет.

## 10. Холодный старт, отказ до порта и сигнал остановки

`docker compose up --build` на пустом volume поднимает PostgreSQL и только после `service_healthy` запускает приложение. У сервиса `app` своего healthcheck в compose нет. Готовность — это дойти до `listen`. Пароль и URL из compose в конспект не копируются: это локальные значения файла compose, не текст заметки.

Команда контейнера — `docker-entrypoint.sh`:

```sh
set -eu
/app/node_modules/.bin/prisma migrate deploy
/app/node_modules/.bin/prisma db seed
exec node /app/dist/main.js
```

`set -eu` обрывает shell на ненулевом коде. `migrate deploy` накатывает уже написанные миграции. `migrate dev` в этот путь не входит: та команда для новой миграции, она умеет спрашивать и создавать файлы. Seed идёт следом. `exec` подменяет shell, поэтому SIGTERM получает процесс Node, а хуки из `src/main.ts` успевают закрыть Prisma. `main.ts` про миграции не знает.

В Nest REST миграции часто запускают руками до `start:dev`. Здесь ручного шага нет: пустой volume должен сам дойти до Sandbox.

Образ многостадийный, база `node:26-bookworm-slim`, в нём стоит `openssl`: schema engine Prisma нужен он на bookworm. На стадии сборки `prisma generate` получает одноразовый `DATABASE_URL` только на эту команду. `prisma.config.ts` читает переменную при загрузке, а generate соединение не открывает. В инструкции `ENV` образа этот адрес не записывается. Дальше `nest build`.

В рантайм копируются `dist`, `prisma`, `prisma.config.ts`, каталог `src/generated` и полный `node_modules`. Seed запускается через `tsx` и импортирует сгенерированный клиент из `src/generated`, поэтому каталог нужен рядом с исходным `prisma/seed.ts`, а не только внутри `dist`. Prisma CLI, `tsx` и `dotenv` стоят в devDependencies и остаются в образе: ими пользуются migrate и seed.

Платим длинной командой старта, идемпотентным seed и более тяжёлым образом. Биография задаётся текстом seed, не слоем Dockerfile. Если migrate или seed падают, `node` не запускается и порт не открывается.
