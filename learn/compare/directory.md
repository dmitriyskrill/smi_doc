# Визитка и каталог

Визитка — один человек и один запрос `profile` без аргумента. Каталог — много карточек, общие справочники и те же данные двумя API. Задание каталога записано в `it_smi-hh-analog-server/TASK.md`.

## Что меняется в данных

`Profile` остаётся карточки. Уникальный `ownerKey` становится публичным адресом человека, а не скрытым ключом единственной строки.

`Skill` теряет `profileId`. Название уникально и живёт в справочнике. На карточке остаётся связь `ProfileSkill`: `profileId`, `skillId`, `sortOrder`. Порядок свой у каждого человека, имя общее. Два профиля с «TypeScript» ссылаются на одну строку, и фильтр идёт по id, а не по похожему тексту.

Компания и должность тоже справочники. Компания уникальна по ИНН, должность — по названию. Опыт остаётся строкой одного профиля, но хранит `companyId` и `positionId`, а не текст. Если компании с нужным ИНН нет, seed сначала создаёт эту компанию, затем опыт её выбирает. Повторный запуск ту же компанию второй раз не создаёт.

Проект и ссылка по-прежнему принадлежат одному профилю. Общего справочника у них нет.

## Что меняется в модулях

| Сценарий | Модуль | Кто ходит в базу |
| --- | --- | --- |
| Открыть карточку, список карточек, опыт, проекты и ссылки | `profile` | `profile.repository`: скаляры и пакетные выборки по id профилей |
| Справочник навыков, число людей, люди с навыком | `skills` | `skills.repository`: один запрос справочника или один запрос связи |
| Справочник компаний, число людей, опыты компании | `companies` | `companies.repository`: один запрос справочника или один запрос опытов компании |
| Справочник должностей, число людей, опыты должности | `positions` | `positions.repository`: один запрос справочника или один запрос опытов должности |

`profile` импортирует `skills`, чтобы превратить название фильтра в id навыка, и импортирует `companies` с `positions`, чтобы пакетно подставить справочник в строки опыта. Аналитика справочника карточки не собирает и не вызывает соседний модуль циклом: один SQL в репозитории того справочника, чью сущность спросили.

Таблица опыта общая для трёх сценариев. `profile` читает опыты человека, `companies` — опыты компании, `positions` — опыты должности. Сама строка опыта модулем не становится.

Проект и ссылка остаются входом модуля `profile`. Свой модуль у них появится, если появится собственная жизнь: общий справочник проектов или модерация ссылок.

## Два API, одни сценарии

REST и GraphQL вызывают один сервис. Контроллер и резолвер только принимают форму запроса.

GraphQL не имеет флага «включить всё». Клиент пишет поля, `@ResolveField` и loader читают только их.

REST так не умеет. Страница каталога, которая всегда хочет имя и навыки, собирается в контроллере: сервис отдаёт скаляры, репозиторий одним запросом отдаёт навыки найденных id. Полная карточка с опытом и проектами включается явным `include`, иначе `GET /profiles` тащит дерево, которое клиент не просил. Это та же цена, что у безусловного `include` в Prisma.

Число обращений к базе на список карточек с навыками: два. Профили — один запрос. Навыки всех этих профилей — второй. Опыт в этот ответ не входит, пока его не попросили.

## Что в визитке не трогаем

`it_smi-server` остаётся одним владельцем и одним GraphQL. Каталог не переписывает тестовое: на собеседовании правят визитку, а не справочник.
